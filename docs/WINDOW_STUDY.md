# RAGuard 2.0：有限幂等保护窗口下的 Agent 副作用恢复实证研究方案

> 状态：正式选定的研究问题与可执行实验规范（不是投稿日程、不是已获得的论文结果）  
> 记录日期：2026-10-25  
> 目标分支：`2.0`，只增补研究与实验文件，不修改 `main`、历史实验或发布标签。  
> 文档性质：本研究的问题定义、已核实依据、实证设计与实施边界；需要时应以新提交修订，不覆盖历史负面结果。

## 1. 唯一研究问题

**中文拟题：**《有限幂等保护窗口与作用域约束下 AI Agent 外部副作用恢复的安全边界：一项公平配对实证研究》  
**英文拟题：** *When Idempotency Protection Expires: A Paired Empirical Study of Safe Agent Side-Effect Recovery*

**RQ：** Agent 的长期持久恢复发生在服务端幂等键的有限保留期限之外，或者恢复时跨越服务端实际幂等作用域时，已有的安全恢复策略会产生多少重复物理副作用、错误确认、未完成任务和额外开销？在**两组拥有相同的服务端契约、业务身份、正向证据及资源预算**时，结果如何变化？

研究对象是**长期恢复与短期服务端去重的契约失配**，不是重新发明 Idempotency-Key、通用重试、Saga、轮询或 exactly-once。

### 需要特别回答的三个子问题

- **RQ1：时效边界。** 保护窗口内、窗口边界、窗口外以及实际清理时间未知时，哪些重试是可验证地安全的？若先前请求仍可能在途提交，单凭年龄处于窗口内是否仍不足以授权？
- **RQ2：作用域边界。** 相同的业务动作和相同幂等键，在 tenant/account、区域、可用区、端点或操作类别变化时，会否成为新的物理效果？能否通过服务端可验证的作用域契约阻断？
- **RQ3：公平恢复取舍。** 让真正独立的 B5 耐久强基线与 RAGuard 同时获得这些契约信息以后，安全性、确认率、停止率、网络回读、运行延迟是否仍存在稳定而可解释的差异？若没有，承认持平并讨论服务端契约，而不是宣称 RAGuard 算法领先。

## 2. 已核实的公开依据及其可用边界

| 来源（已核实页面可达） | 可以支持的事实 | 不能推出的事实 |
| --- | --- | --- |
| [Stripe Idempotent Requests](https://docs.stripe.com/api/idempotent_requests) | 幂等结果记录在键至少满 24 小时之后可以清理；清理后重复使用原键可以触发新请求；校验同键参数一致性 | 不能把「至少 24 小时后**可能**清理」写成「恰好 24 小时必然清理」 |
| [Shopify GraphQL Admin Implementing Idempotency](https://shopify.dev/docs/apps/build/apis/graphql-admin/implementing-idempotency) | **适用 `@idempotent` 指令的部分 mutation** 具有 24 小时去重保护及并发、参数不匹配语义 | 不能推广到 Shopify 的全部 API 或所有 mutation |
| [AWS EC2 API Idempotency](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html) | EC2 不同操作可采用区域级／可用区级幂等；跨作用域相同 token 可能成功创建额外资源 | 不能泛化到所有 AWS 服务，也不能据此臆造 EC2 的固定 TTL |
| [IETF HTTPAPI Idempotency-Key draft-08](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-08) | 2026-10-22 草案提出资源方应明确相关键的过期策略、唯一性和参数指纹要求 | **仍为 Internet-Draft，并非生效的正式 RFC** |
| [LIMBO, arXiv:2609.29095](https://arxiv.org/abs/2609.29095) | 已研究未知提交、延迟提交、幂等契约与 Agent 重复副作用，构成直接强重叠工作 | 不能将「有幂等键优于没有」或「未知提交不能盲重试」再次申报为创新 |
| [PayPal API Requests](https://developer.paypal.com/api/rest/requests/) | `PayPal-Request-Id` 是否可用及存储期具有端点依赖性；官方示例说明部分请求可在给定期间重试 | 不能认为所有 PayPal 端点均统一 45 天 |

**严格区分：** `min_guaranteed_retention`（有官方或可验证契约支持的最低保护期）、`actual_eviction_at`（服务端实际清理时间）、`first_server_seen_at`（服务端首次接收/开始处理）和 `first_client_sent_at`（客户端记时）。四者不等价；不能把客户端时钟与服务器端过期边界直接当作可精确比较的事实。

## 3. 核心假设及可证伪标准

**H1（反例重现）：** 即使业务键不变，恢复于服务端已删除记录之后仍可能出现第二次物理效果。这是已知机制验证，不计作独立创新。

**H2（作用域风险）：** 相同键跨幂等作用域可能引入额外物理效果，且网络响应 `200` 不等于原业务动作在正确作用域完成。

**H3（安全与可用性）：** 当保护范围或期限无法证明时，保守停止/回读策略能减轻危险重复，但会增加未决任务；这一代价须定量呈现，而不是只比较「无重复」。

**H4（公平性底线）：** 若 B5 拥有同等契约信息和恢复权限后与 RAGuard 完全持平，必须承认其结果；仅仅增加一个时间比较 `if` 不构成方法创新。

**H5（可能有论文价值但需检验）：** 多来源、不同时间/作用域/并发保证的契约矩阵能够产生**现有研究未充分分层量化**的策略排名逆转、可靠性边界或实际成本曲线；如果全文对比已有文献后也无独立贡献，则改为公开负面基准或放弃投稿，而不是制造优势。

## 4. 实验体系：两个相互独立的层次

### A. 已完成的 Python 确定性先导（仅证明机制）

先导源码保留于独立交付包 `RAGuard_Idempotency_Window_Pilot.zip`；核心为 `raguard/window_contract.py`、`bench/window_pilot.py` 和 10 项单元测试。120 种条件 × 4 个演示标签＝480 行**确定性合成观测**。三种预设保护期限和五种恢复时刻是**归一化模拟时间**，不是 Stripe、Shopify 或 AWS 真实 TTL。

| 演示标签 | 案例数 | 错误确认 | 不安全案例 | 未完成 |
| --- | ---: | ---: | ---: | ---: |
| 不检查契约的简单重试 | 120 | 30 | 74 | 0 |
| 旧耐久机制简化消融 | 120 | 30 | 74 | 0 |
| B5 契约感知演示 | 120 | 0 | 0 | 66 |
| RAGuard 契约感知演示 | 120 | 0 | 0 | 66 |

上表两个「契约感知」标签使用**同一纯判定函数**，不是独立系统端到端实验；「旧耐久机制」也不是对真实 B5 源码执行结果。不可把以上数字作为正式强基线结果。10/10 项本地单元测试通过（按工程根目录运行）。

### B. 下一阶段必须实现的真实 Go 沙箱配对实验

在现有 Go 沙箱添加**只针对研究的可配置去重域和保留机制**，保留原有默认行为；任何测试都不得发真实支付/邮件/资源创建请求。用真实 HTTP 路由及真实 Python Gateway/B5 入口完成观察，不在恢复决策中读取物理真值。

**最小竖切：** 两个相同业务键的 HTTP `POST` → Go 服务端原子去重表 → 提交后回执丢失 → 控制服务端键清理/换作用域 → 恢复者回读或执行 → 独立效果账本判分。先固定单个域、单个 TTL 边界、一个明确的故障，再增加矩阵；不得一次扩充整个架构。

**基础变量（逐层扩展，不机械做全笛卡尔积）：**

1. `first_effect`: 未提交 / 已提交但丢回执 / 请求仍在处理；应另外记录真正的物理效果发生时刻；
2. `retention_state`: 保证期内 / 边界处 / 清理后 / 保证期限未知；保证期的保守含义由服务端实现给出；
3. `scope`: 完全相同 / Region 变更 / Zone 变更 / 业务主体变更 / 接口契约不适用；
4. `readback`: 可信即时正向 / 延迟最终一致 / 不可读 / 来源不匹配；阴性回读不能证明没有晚提交；
5. `execution`: 正常恢复 / 原执行者死于写入前后 / 3–8 个恢复进程并发争用；
6. `time_uncertainty`: 可靠服务端时间 / 客户端—服务端时钟偏差 / 请求传输与在途提交时延上界未知；
7. `repeat`: 每个条件在独立沙箱上多次运行并保存种子、版本、异常栈和独立 oracle 真值。

**必须检验的反例：** 在未知在途提交上界的情况下，即使两次请求都处于标称 TTL 内，也不应仅凭「年龄尚小」断言重试必然安全；这一点直接对照 LIMBO 的相关限制。

## 5. 真实基线必须一致而不故意放水

| 方法 | 对照目的 | 特别限制 |
| --- | --- | --- |
| B0 不重试 | 安全停止及未完成率下界 | 不能只据其较低完成率声称新方法优秀 |
| B1 无契约简单重试 | 可解释的反面消融 | **不是**强基线 |
| B5 真实 DurableBaseline | 独立 SQLite 耐久机制对照 | 使用原有 `bench/durable_baseline.py`，不得伪装成简化标签 |
| B5 + 契约信息 | 信息对等的最强实际对照 | 与 RAGuard 共享同等 TTL、scope、时钟余量和正向回读能力 |
| RAGuard 现有 Gateway | 当前维护版本 | 不改变历史冻结策略的安全门禁 |
| RAGuard + 契约信息 | 候选改进对照 | 改进逻辑必须与执行权/证据处理明确分离；不允许访问 oracle |

另外可以计算「可见真值的理想策略」作为诊断上界，但**严禁将它作为可部署策略**或隐藏地给候选方法提供实验真值。

## 6. 明确的公平条件和测量指标

每组配对共享相同业务意图、随机种子、Provider 规则、故障、证据机会、观察截止时刻和总查询/等待预算；独立启动沙箱并重置物理效果。评价器与两组策略严格隔离，保留完整的物理效果轨迹。

**主要指标**：`duplicate_physical_effects`、`wrong_scope_effects`、`false_confirmation`、`acknowledged_completion`、`unresolved_or_escalated`。  
**辅助指标**：`actual_http_attempts`、`evidence_reads`、`wall_clock_latency_ms`、`runtime_restart_count`、`budget_consumed`。

- **确认成功**必须同时满足正确作用域存在预期的物理效果、无额外效果、恢复系统也获得可采信正向确认。
- **错误确认**表示系统报告成功但 oracle 中没有正确业务效果；跨区域新建效果也必须单独计为危险结果。
- 采用严格配对统计：按 TTL 区间、故障类别、作用域和 Provider 分层；二元结局可报告配对差值及置信区间，连续成本用重复实验与自助法区间。零观察到的不安全事件不能据此宣称风险为零。
- 输出 `episodes.csv`、`paired_summary.csv`、`fault_contracts.json`、`REPORT.md` 和复现命令；负面结果一并保存。

## 7. 工程结构与代码质量要求

基于现有仓库，不建立第二套可混淆的 Gateway。先新增隔离实验文件，必要时最小化扩展 `mock/main.go` 及其 Go 测试；不直接修改生产网关的重试授权。建议结构：

```text
raguard/
  window_contract.py          # 纯契约判定，不访问外部服务
bench/
  window_live.py              # 真实 B5 / RAGuard 配对驱动
  test_window_live.py         # 测试外部行为和负面边界
mock/
  main.go                     # 研究模式可配置的键保留与作用域
  main_test.go                # Go 物理去重和过期临界测试
docs/
  WINDOW_STUDY.md             # 本研究正式方法与证据，保留旧记录
```

按此前提供的 `Skills Main` 原则做**最小垂直切片、行为层测试、两轴审查**：先验证输入输出，再加代码；注释写清楚非显而易见的安全不变量，全部中文、避免 AI 风格长分隔线；与现有公共模块尽量保持接口兼容。测试必须包含「过期仍发生重复的反例」和「作用域错误不准确认」；没有可验证数据就标注 `UNVERIFIED`，不得猜测。

本研究不需要 GPU；启动前优先检查已安装 Go（本仓库 CI 使用 Go 1.23）和 Python 3.12。构建、测试和 CI 应使用已记录的固定环境；因平台差异而跳过测试必须在报告中注明。

## 8. 研究通过、失败与停止条件

**工程通过**：合成先导复现；Go 去重 TTL/作用域单元测试通过；两个真实客户端配对完全对齐；Windows/Linux CI 通过；源码 manifest、UTF-8 与隐私检查通过。

**科研继续条件**：严谨文献对比发现至少一个未被同类工作充分研究的交互边界，且在多次独立配对实验中出现**可重复、可解释**的策略取舍或方法排序变化。论文可以是负面实证结果，但必须有可推广的解释和充足研究设计，而非「我们又实现了键过期检测」。

**立即暂停/重新讨论**：实证风险完全可由已有厂商文档和 LIMBO 结论解释、无法实现独立客观的物理真值、B5 在信息对等后全部持平且没有有价值的新的实证边界、或者仅靠人工挑选场景得到提升。先汇报负面结果，禁止为了投稿伪造「创新」。

## 10. 下一步直接执行的第一个验证任务

**任务：有限 TTL 和变更作用域的 Go HTTP 真值实验（最小竖切）。**

输入：`key`、`scope`、请求摘要、模拟服务端接收时刻、可配置的最短保证窗口与实际清理时刻。  
输出：首次提交效果 ID、同键保护期内回放、清理后出现的独立效果 ID、跨作用域效果记录以及只供评价器使用的历史。

**验收样例（独立于实现写死）：**
1. 同 scope、同 key、相同 payload、保留未失效：网络请求 2 次，物理效果恰好 1 个。
2. 同 scope、同 key，已确认服务端键被清理：物理效果恰好 2 个；不得用「同键」消除该物理差异。
3. 不同 scope、相同 key：可发生各自的独立物理效果；跨 scope 回执不可用于确认原业务。
4. 首次提交未知且回读不可用：策略不能依据 absence 或 TTL 猜测已提交/未提交；无可信执行许可时安全停止。
5. 同时到期、时钟偏差和多个恢复者竞争：必须明确临界边界和 CAS 胜者，未测前不得宣称完整实现。

任务完成后才将**真正的** B5/RAGuard 接入，不会把先导 Python 演示标签作为正式结论。完成物理实验时另增源码与测试提交，不覆盖本方案与旧实验。
