# 实验定义与边界

## 真值与业务键

每个故障试验由固定的独立业务键和真实 Go 效果 ID 判分。业务键来自受控实验 fixture，不来自 Agent 可自由改写的 `intent`。同一业务动作修改意图仍计为重复效果；不同业务键被视为不同合法操作。沙箱实验不模拟生产平台跨租户身份授权。

- `acknowledged_success`：业务最终效果达到目标，调用方也收到确认。
- `physical_goal`：仅由独立效果事件判断的最终状态。
- `unsafe`：历史重复提交或额外未知业务提交，即使后来补偿也不会抹掉。
- `escalated`：未确认任务完成，需要停止或人工处理。
- `attempts/readbacks/extra_calls`：实际网络试验开销；`latency_ms` 是本轮策略时延，不含启动/销毁沙箱。

## 公平比较

单步骤方法 B0（不恢复）、B1（无约束固定重试）、B2（新意图指数退避）、B3（稳定幂等键+正向回读+硬停止）与 RAGuard 在同一工具/故障/强度/种子下配对，每次新建独立沙箱。单步故障六类：提交前断连、429、503；提交后断连、损坏 JSON、响应篡改。五档强度是 0/1/5/10/20%，另有 100% 强制故障冒烟。

多步骤 B4 是**本地参考 Saga**：使用 SQLite 持久步骤日志、正向确认、崩溃后不盲重发未知副作用及反向补偿。只与 RAGuard 在同一固定工作流、同一真实沙箱下比较。它不是 SagaLLM 官方代码，也不应与单步骤指标平均。

## 统计完整性

使用相同工具/故障/强度/编号/种子做严格配对。缺失配对、重复试验键不再静默忽略。Bootstrap 为描述性区间，综合不同业务和故障时必须同时报告分层分析。1% 故障下少量试验无法保证统计功效，未完成正式 RQ 验收。

## 业务重规划与证据失效对照

执行 `python -m bench.identity_drift --repeats 1 --output results/identity_drift`。实验固定业务键和参数，仅在第二次调用改写 Agent 的 task/step/intent，并将两次调用放在同一独立 Go 沙箱中观察历史效果。每个工具、故障、回读状态和方法构成一个独立实验条件，首轮共 54 个 Episode。结果写入 CSV 和简短报告。

- `b3_step`：仅有步骤级键的幂等恢复；Agent 改名后键变化。
- `b3_business`：给予 B3 相同业务身份的更强对照；不具备 RAGuard 的本地执行账本，在原生幂等写入中可能持平。
- `raguard`：可信业务绑定与可恢复账本，证据不足时安全停止。

`duplicate_effects` 根据外部物理效果记录统计，`unsafe` 包含重复或未知业务效果；`renamed_status != 200` 为未完成，不得计入成功。B3 变体不是完整生产系统，结果只能检验实验中的身份契约与停机取舍，不能声称普适领先。

## 独立耐久强基线（B5）

新增 `bench/durable_baseline.py`，单独实现可信业务键、SQLite 写前日志、进程恢复、正向证据回读与安全停止，不调用 RAGuard Gateway。这是公平实验参考实现，而非外部商用系统官方复现。

运行 `python -m bench.identity_drift --repeats 1`。首轮 72 个 Go 沙箱隔离案例，各方法 18 个：步骤级 B3 重复 18 次；业务级 B3 重复 12 次；B5 与 RAGuard 均零重复、7 次第二次未完成。方法在当前场景持平，不能继续用该结果声称新系统领先。下一轮应检验证据暂时不可用时的**有界等待与安全恢复**，联合报告完成率、未决率和成本。

## B5 与 RAGuard 共享证据策略的公平性核验

运行 `python -m bench.evidence_parity --output results/evidence_parity`。两组实验分别标记 `b5_durable` 和 `raguard`，但目前**都调用相同的只读 `assess_evidence` 函数**，尚未连接完整 B5/Gateway 的实际写入路径。本阶段只验证相同证据规则在相同合成事件序列上的决策一致性，不能据此声称 RAGuard 优于 B5。

固定 16 类证据轨迹，两组方法各 16 条，共 32 条合成记录，涵盖延迟提交、提交不可观测、业务引用不匹配、请求摘要错误、未经验证的来源、过期证据、权限代次变化、冲突回执。每条轨迹有独立的隐藏物理真值。WAIT 只允许继续收集证据，**不授权重新执行外部写入**。

| 方法标签 | 合成轨迹 | 错误确认 | 已确认 | 未完成 | 查询次数 | 虚拟等待秒数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| B5 | 16 | 0 | 4 | 12 | 74 | 58.0 |
| RAGuard | 16 | 0 | 4 | 12 | 74 | 58.0 |

上述数据来自本地合成轨迹，不包含 Go 沙箱写入、外部 API 调用或真实网络时延。下一步需在相同的真实 Go 故障条件下接入经验证的 Provider adapter，比较完整网关的安全性、任务完成率、升级率、网络开销及墙钟时间。

## Go 真实回读证据的端到端对照

使用 `python -m bench.evidence_live --repeats 1`。每个实验组合运行独立 Go 沙箱，Go 回读增加业务键、执行指纹、效果 ID、版本、观测时间与本地权威代次；两组恢复流程均经 `LocalEvidenceClient` 检查相同的 `assess_evidence` 规则。旧 Windows 内置沙箱没有这些新增元数据，**本实验需要 Go 1.21+ 编译源码**；普通 Windows 演示不受影响。

首轮本地受控实验：96 条真实 HTTP 沙箱 Episode，B5 和 RAGuard 各 48 条，均 0 错误确认、0 重复/未知副作用、22 条未完成。B5 回读 81 次，RAGuard 回读 118 次。其余情形包括提交后断连、回读不可用、错误业务键/指纹、陈旧时间、错误权威代次、未最终确认。结果说明在同等证据准入条件下尚无独立安全优势，且 RAGuard 查询开销更高。需要后续优化并检查策略的公平性。

`verified` 的含义仅为“**受控本地回环沙箱给出的来源数据满足实验配置**”，而不是外部密码学签名或第三方 Provider 身份认证；沙箱效果历史只供实验评价器读取，不用于恢复决策。以上探索性数据不可作为正式论文结论。
