# RAGuard 两条投稿路线的阶段审查

## A：条件证据规划算法

候选方法：在预算约束下，依据来源权威能力、校准场景与历史回读选择下一条查询，并由已有的安全恢复判定器单独授权确认。

当前实现：`bench/evidence_closure_planner.py`，包含一个有限状态穷举规划器。其目标是最大化模型内安全确认概率；没有证明它在更广泛问题上优于现有 POMDP、贝叶斯实验设计、动态规划或主动信息获取。穷举在来源和状态变多时会迅速变贵，也没有生产级签名、撤销、fencing、安全重发能力。

本地最小案例：给定四个等权场景，预算为 3。选择条件路由查询后再选择匹配证明源，可确认 2/4；固定查询某单一证明源只确认 1/4。但手工的“先路由、后对应证明源”也能确认 2/4，因此**不能把这种差异称为新算法优势**。

待证伪问题：服务端多代次、证据时效与冲突、多个身份范围、查询依赖与跨回合未知模型下，条件规划能否保持安全，并在相同真实成本下超越结构化规则、现有信息价值规划及预算型 POMDP 基线？若不能，放弃新算法优越性主张。

## B：科研软件及安全边界评测

现有能力：真实 Go HTTP 故障注入、独立 B5/RAGuard 持久恢复、物理效果真值、限制幂等窗口、晚提交、证据来源可见性、强基线配对、多种预算协议、CI 与结果完整性清单。

存在的差异风险：既有 LIMBO 等工作涵盖未知提交与 Agent 工具调用。需要进行逐条规格比较，不得仅凭软件仓库数量或测试数量声称独创。尤其应明确：不能保证通用 exactly-once；现有 B5 同信息实验持平；无商业厂商真实事故分布验证。

## 判定

A、B 均保留，但算法候选暂定为**可行性原型**，不得称为创新算法已经验证。B 已更接近形成可复现材料，但仍需全文查新、独立环境复现和投稿目标的正式审核。两条路线可以共用沙箱，算法假设与结果不能混淆。
