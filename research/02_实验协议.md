# RAGuard · 预注册实验框架

状态：**研究方案，不是已跑完的结果**

## 研究问题

- RQ1：在双方结果不可区分的失败下，安全准入能否减少重复副作用？
- RQ2：与强幂等键防重/回读/补偿相比，是否能提高合法完成率或降低时延与升级率？
- RQ3：服务支持程度、回读延迟、并发、故障强度变化时，安全性边界在哪里？

## 样本单位

一组实验的单位是完整的**任务 episode**。固定 `task_id × world_seed × fault_schedule`，比较方法均使用相同业务初始状态、相同故障时序，不因某方法提前终止而改变注入对象；结果基于独立服务端事实账本。

## 服务与故障

- 三业务域：订单+库存、工单+CRM、文件/云资源（均为本地假服务）
- 至少涵盖：read-only、服务端幂等写、可补偿写、不可逆写、无回读写、最终一致回读
- 故障：提交前断连、提交后响应丢失、延迟提交、重复投递、429、503、回读滞后/不可用、schema drift、响应异常、部分批量提交
- 注入强度：0/1/5/10/20%；每条件先 ≥30 个配对种子做 pilot，样本量随置信区间宽度与统计功效调整
- 测试并发：1/10/50，记录资源配置和环境；不能把 SQLite 锁瓶颈隐藏成策略优势

## 业务级判定（初步可运行代码在 `bench/oracle.py`）

- `task_success`：最终仍生效的业务操作等于期望，且没有未请求的操作
- `duplicate_executions`：历史发生的超额物理写入次数；即使后续补偿，历史重复仍存在
- `exactly_once_success`：任务成功，且历史没有多做/误做写操作
- `recovery_success`：在实际发生注入故障的任务中合法完成的比例
- `false_safe`：被准许重复执行却导致违约的样本比例（独立标注动作许可）
- `escalation`, `p50/p95/p99`, `extra_calls`, `cost`, `CPU/RAM`, `readback_count`

报告**原始成功/总任务数、绝对百分点、配对 bootstrap 95% CI**；对于条件性安全，不把在有限试验中零违约写为数学证明。

## 原则上必须完成的消融

1. 不检查业务唯一键 / 使用 Agent 任意命名的 intent
2. 不用可信回读，只保留可靠执行回执
3. 不用状态证据有效期，只以 HTTP 成功判定
4. 不用代次 CAS / 依赖约束（在沙箱做安全负测）
5. 不用成本选择，只使用最保守安全规则
